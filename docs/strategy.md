起点の実測（2026-09-22）: **IG フォロワー 3 人 / 投稿 180 件**。数字が伸びていないのではなく、**ほぼ誰にも届いていない**状態からの再出発。

### 判定窓・経過日・次の判定日と集計

d = 今日 − S（日数。日付はすべて JST）

| 条件 | 経過日 | 判定窓 | 次の判定日 |
|---|---|---|---|
| d < 0 | 未開始（S が未来の日付 = 台帳の書き間違い。前の試行の行・前回モード・方針をそのまま続け、レポートの「注意」行に書く） | — | — |
| d ≥ 14 かつ d が 14 の倍数 | **判定日** | (今日 − 14)..(今日 − 1) | 今日 + 14 |
| それ以外 | Day (d mod 14 + 1) / 14 | max(F, 今日 − 13)..今日 | S + 14 × (floor(d / 14) + 1) |

例（S = 2026-09-14）: 09-15 は Day 2 / 14・判定窓 09-02..09-15・次の判定日 09-28。09-28 は判定日（判定窓 09-14..09-27）。09-29 は Day 2 / 14（次の判定日 10-12）。

**毎朝の集計は `node scripts/pdca-summary.mjs`**。上の表・下の判定指標・閾値・モードの決め方（前回レポートのモード列の引き継ぎ、判定日と遅延判定）を実装しており、レポート冒頭の節をそのまま出す（テスト: `scripts/pdca-summary.test.mjs`）。正本と同じ定義の jq 版（突き合わせ用）は、S と F を台帳の値にすれば、今日の日付から判定窓・経過日・次の判定日・判定指標をまとめて出す（日付を手で書き換えない）。IG と YT で S / F が違うときは行ごとに実行し、該当する側の数字を使う。

```bash
TODAY=$(TZ=Asia/Tokyo date +%Y-%m-%d); S=2026-09-14; F=2026-04-20
jq -r --arg today "$TODAY" --arg s "$S" --arg f "$F" '
  def day: strptime("%Y-%m-%d") | mktime / 86400 | floor;
  def ymd: . * 86400 | strftime("%Y-%m-%d");
  def median: sort | if length==0 then null elif length%2==1 then .[(length/2|floor)] else ((.[length/2-1]+.[length/2])/2) end;
  ($today|day) as $t | ($s|day) as $sd | ($f|day) as $fd | ($t - $sd) as $d
  | if $d < 0 then "today=\($today) status=未開始"
    else
      (if ($d >= 14 and ($d % 14) == 0) then {status:"判定日", from:($t-14|ymd), to:($t-1|ymd), next:($t+14|ymd)}
       else {status:"Day \(($d % 14)+1) / 14", from:([$fd, $t-13]|max|ymd), to:$today, next:($sd + 14*((($d/14)|floor)+1)|ymd)} end) as $w
      | [.videos[] | select(.date >= $w.from and .date <= $w.to)] as $v
      | ($v | map(select(.stats.updatedAt != null) | (.stats.views // 0))) as $yt
      | ($v | map(select(.instagram != null and .instagram.views != null) | .instagram)) as $ig
      | "today=\($today) status=\($w.status) window=\($w.from)..\($w.to) next_judgment=\($w.next) posts=\($v|length)",
        "YT views median=\($yt|median) (n=\($yt|length))",
        "IG views median=\($ig|map(.views)|median) saved_sum=\($ig|map(.saved // 0)|add // 0) (n=\($ig|length))"
    end
' data/performance-history.json
```

- 過去の判定日 J の判定（遅延判定）を出すときは、`TODAY` に J を入れて実行する（status=判定日、判定窓 (J − 14)..(J − 1) になる）
- jq の日付関数が使えない環境では、上の表どおりに `date -d` で判定窓を出し、同じ条件（YT は `stats.updatedAt` あり、IG は `instagram.views` あり）で中央値と合計を出す

### 判定指標

- **IG**: 判定窓の `instagram.views` の**中央値**と、`instagram.saved` の**合計**（別々の 2 指標で、足さない）。`instagram` か `instagram.views` が null の回は除外
- **YT**: 判定窓の `stats.views` の**中央値**。`stats.updatedAt` が null の回は除外
- n は IG / YT で別々に数える。**n < 7 なら判定保留**。IG と YT の数字を足したり平均したりしない
- 朝ルーチンの時点では当日分は未投稿で、前日分も統計・insights が未取得のことが多い（除外されるので、通常日の n は最大 12 前後）
- **このアカウントの例外（2026-09-22 オーナー決定・集客フェーズ）**: **モード**（通常 / 切替候補 / 配信死亡モード）は上の指標と下の閾値どおり views 中央値と保存合計で機械的に出す。ただし**この型を続けるか切るかの判断は IG のフォロワー増加数を主指標にする**（起点 3 人の絶対値。views は集客フェーズの進み具合を測れない）。フォロワー数は自動取得していないので、判定日にオーナー / 司令塔が実測値を入れる

### モードの決め方（毎朝、アカウントごと）

モードは `通常` / `切替候補` / `配信死亡モード` の 3 つ。**モードが変わるのは判定日（と遅延判定）だけ**で、それ以外の日は前回モードを続ける（行ったり来たりを防ぐ）。

1. **前回モード** = `docs/pdca/` の `YYYY-MM-DD.md` のうち、**今日より前の日付で「ジャンル試行の状態」表のモード列が読める最新のもの**のモード列。表の無いレポート（「未導入」の 2 行だけ・ルーチンの失敗など）は飛ばして、さらに前の日付を見る。1 本も無いときだけ、上の台帳の「導入時の判定」（配信死亡 → `配信死亡モード（2026-09-14〜）`）。**新しい試行が始まっても前回モードを引き継ぐ**（新しい試行の最初の判定日に、その試行の数字で判定し直す）
2. **遅延判定**: 今日より前の直近の判定日 J について、J 以降の日付のレポートに「ジャンル判定」節が無ければ（ルーチンの失敗・導入の遅れなど）、今日まず J の判定を窓 (J − 14)..(J − 1) で出し、3. の判定日と同じ扱いでモードを決め直してから今日の分に進む。判定日は S + 14k（k ≥ 1）だけで、S 当日（2026-09-14 の「導入時の判定」）は判定日ではないので、遅延判定の対象にしない
3. **決定**:
   - **今日が判定日（または遅延判定）** → 判定値どおり: 配信死亡 → `配信死亡モード`（前回から続くなら宣言日はそのまま、新しく入るなら宣言日 = その判定日）/ 切替候補 → `切替候補` / 続行 → `通常` / 判定保留（n < 7）→ 前回モードのまま
   - **それ以外の日** → 前回モードのまま。今日の判定値が配信死亡なのにモードが `配信死亡モード` でないときは、レポートに「注意」行を書く（モードの変更は次の判定日）

### 通常・切替候補のときの日次 PDCA

- 柱・抽出法の比較は、**型の初回投稿日 F 以降の回だけ**で行う（新しい型の序盤に古い型の数字を混ぜない。回数が少なければローテーション寄りでよい）。比較に使う「直近 14 日」は判定窓とは別で、**今日より前の 14 日**（今日 − 14..今日 − 1）
- 比較は**アカウントごと**（IG はフォロワー増加数と保存数が主指標、YT は views を別に参考。合算スコアを作らない）。「伸びた軸を続ける」判断は、配信死亡モードでないアカウントの数字から行う
- 切替候補のアカウントは、判定日に次ジャンル候補を 2〜3 案出す（このリポの制約を守る）。日々の最適化は通常どおり続ける

### 配信死亡モード中の日次 PDCA

1. **性能データで軸を最適化しない**: 配信死亡モードのアカウントの数字で、柱・抽出法の TOP/WORST 比較や「伸びた軸を続ける」判断をしない（0 と 1 を比べても何も分からない）
   - **2 アカウントとも配信死亡モード** → 柱・抽出法は**性能データで選ばない**。`pdca-summary.mjs` の「ローテーション」で**直近 14 日の使用回数が少ないもの**から、「同じ柱・抽出法を 2 日連続にしない」を守って選ぶ（同数なら下の「コンテンツの柱」表・`METHODS` の上から）。軸別の表は参考表示のみ
   - **片方だけ配信死亡モード** → 比較は**生きている側のアカウントの指標だけ**で行う。生きている側も判定窓の n < 7 で指標が使えない日は、2 アカウントとも配信死亡モードのときと同じ選び方（ローテーション）をする
2. **提案は構造実験だけ**: タイトル個別化 / 型変更 / ジャンル変更。各提案に「何を変えるか / 何で測るか / 14 日後の合格ライン」を書く。合格ラインの既定は上の閾値表の「続行」域（IG: views 中央値 ≥ 50 または保存合計 ≥ 5 / YT: views 中央値 ≥ 20）で、配信死亡を抜けるだけの線を合格にしない。同じ動画を IG と YT に出しているので、動画そのものを変える提案（型変更・ジャンル変更）は `IG / YT 共通` の 1 行にまとめてよい。片方だけの変更（タイトル個別化など）はアカウント別に書く
3. **提案はレポートに書くだけ**: 当日の原稿・タイトル・`data/enriched-coffee-news.json` には反映しない（型・スキーマは下の「データスキーマ」どおり。反映すると動画生成が失敗しうる）。次ジャンル候補や構造実験は手持ちのデータと知識で短く書き、Web 調査に時間を使わない（原稿と JSON の書き出しを優先する）
4. **新しい試行が走っている間**（試行 #2 以降で、まだ最初の判定日前）は、「構造実験の提案」節に `実行中: 試行 #n（<ジャンル / 型>）Day N / 14` とだけ書き、追加の提案は判定日まで控える（変数を増やさない）。試行 #2 が main に入っていてまだ新型の初回投稿が無い間も同じで、`準備中: 試行 #2（<ジャンル / 型>）` とだけ書き、同じ案を毎朝書き直したり別案を足したりしない（`pdca-summary.mjs` がこの行を出す）
5. **このリポの制約（2026-09-22 オーナー決定で変更）**: いまは**集客フェーズ**。ジャンル・型は変えてよいが、**自社の豆・産地・銘柄・販促の導線を出す型は候補にしない**。候補は「視聴者が自分の持ち物で今日試せる知識」の型に限る（例: 抽出の変数、器具の比較、味の直し方、保存・器具の手入れ）。販促の型に戻すのはオーナーが IG フォロワー 2,000 人で判断する
6. **投稿は止めない**。原稿の作成は通常どおり。型の切替は人間が決めて PR で入れる

| キー | 柱 | 扱う例 |
|---|---|---|
| `temp` | 湯温 | 3 度下げると何が変わるか / 高温で甘みを出す / 温度計が無いときの目安 |
| `grind` | 挽き目 | 1 段細かく / 粗くして雑味を消す / 挽き目と落ちる速さ |
| `ratio` | 粉と湯の比率 | 1 対 15 を基準にする / 濃く淹れる / 薄いと感じた時 |
| `time` | 抽出時間 | 30 秒早く止める / 浸けて待つ / 落ち切りを待たない |
| `pour` | 注ぎ方 | 蒸らしの秒数 / 注ぎ回数 / 注ぐ速さと太さ |
| `gear` | 器具の違い | 円錐と平底 / 紙と金属 / 浸漬式と透過式 / アイスの急冷 |
| `trouble` | 味の直し方 | 酸っぱい / 苦い / 薄い / えぐい をどう直すか |
| `nogear` | 器具がなくてもできる | マグひとつで / スーパーの粉でも味は動く / 計量スプーンでの目安 |

各回は「問い（hook）→ 答え（topic）→ 理屈（why）→ 数字 → 手順 → こう変わる → うまくいかない時」の 1 本道。視聴者が**その日のうちに 1 つだけ試せる**ことを条件にする。

## 絶対に出さないもの（NG）

`scripts/brand-guard.mjs` が**データから組み立てられる**動画テキスト・ナレーション・YouTube タイトル・説明文・タグ・Instagram キャプションを機械的に検査する（`collectPublishedTexts`）。検証時（`validate-content.mjs`）と**投稿直前**（`check-published.mjs`、pipeline Step 5d と再投稿系ワークフロー）の 2 回走り、1 つでも当たれば原稿は常備ネタ帳に差し替わるか、ジョブが赤くなって投稿されない。テストは `scripts/brand-guard.test.mjs`。
**この検査が届かないのは、コンポーネントに直書きされた固定文字列だけ**（いま該当するのは下の「意図的な例外」のブランド表記 1 つ）。新しい固定文字列を画面に足すときは、この節を読み直すこと。

1. **自社の豆**: `data/coffee-lineup.json` の名称・表示名・読み・産地・地域・農園・品種・精製（ファイルから自動で拾うので、豆を足しても消しても効く）
2. **産地名・銘柄名一般**: エチオピア / ケニア / コロンビア / ブラジル …（`ORIGIN_TERMS`）。視聴者が持っていない豆の話になる
3. **屋号・ブランド・ハンドル・EC ホスト**: Open Ground Coffee Roasters / OPEN GROUND / @open_ground_coffee_roasters / open-ground.co
4. **販促の言葉**: ご購入 / 購入 / 販売 / 発売 / 通販 / オンラインショップ / ご注文 / ご予約 / 卸売 / 卸のご相談 / お取り扱い店 / 送料 / 定期便 / お取り寄せ / DM / プロフィールのリンク / 自家焙煎 / 当店 / 弊社 …（`SALES_TERMS`）
5. 常温での長時間浸漬（食品安全。これはブランドガードではなく `unsafeSteepReason` が機械的に弾く）
6. 人間の判断で避けるもの（機械チェックなし）: 健康効果の断定、出典の無い「世界大会の〇〇選手のレシピ」、「コーヒーあるある」「モーニングルーティン」のような**その日に試せない**回

**許されるもの**（誤検知で毎朝 fallback に落ちるほうが害が大きいので、意図的に外してある）:

- 焙煎度: 浅煎り / 中煎り / 深煎り
- 精製・品目の一般語: ウォッシュド / ナチュラル / ハニー / デカフェ / ブレンド …（`GENERIC_WORDS`。自社の豆の名前にたまたま入っているだけで、誰でも使う語）
- 味の表現: キャラメルのような甘さ / シトラス など（`flavor` / `labelFlavor` は検査しない）
- 生活の言葉: スーパーで買える粉 / 豆の取り扱いは密閉容器で / カフェで注文する時は / メーカー公式サイトの推奨値 / 在庫 / 粉を卸すように
- 器具の一般名: V60・カリタウェーブ・ORIGAMI・フレンチプレス・エアロプレス・クレバー・ケメックス・マキネッタ・ペーパードリップ・マグで浸漬

**意図的な例外**: 動画のフッターに入る `OPEN GROUND COFFEE ROASTERS` のブランド表記（`src/cards/primitives.tsx` の `Brand`）。これは**アカウントの署名**であって商品の宣伝ではなく、オーナー決定「アカウント名は変えない」と揃えている。外すかどうかはオーナー判断。

## CTA（集客）

販促の CTA は全廃した。動画の最後と、キャプションの末尾は固定文言（`growthCtaSlideLines` / `growthCtaCaptionLines`）:

- 動画: 見出し「保存して、次に淹れる時に試そう」／「保存して、淹れる前に見返す」「フォローで、明日もひとつ持ち帰る」
- キャプション末尾: 「毎朝ひとつ、今日から試せる抽出のコツを出しています。」「保存しておくと、淹れる前にすぐ見返せます。」「フォローすると、明日もひとつ持ち帰れます。」

ハッシュタグも販促語を外した: `#コーヒーの淹れ方` `#ハンドドリップ` `#<器具名>` `#おうちカフェ` `#コーヒーのある暮らし` `#抽出` `#コーヒー`（アイスの日は `#アイスコーヒー` を追加）。

## ペルソナ（優先順）

集客フェーズなので「買ってくれる人」ではなく「**保存してフォローする人**」で並べ替えた。

1. **家で淹れ始めた人（最優先）** — ドリッパーとケトルは買ったが、味が安定しない。数字をそのまま真似したい。保存する動機が最も強い
2. **器具をまだ持っていない人** — インスタントやスーパーの粉から一歩出たい。`nogear` の柱が受け皿
3. **淹れ慣れている人** — 自分の手順を微調整したい。`trouble` と `gear` の柱で拾う

いずれも「自分が持っている豆でできること」しか求めていない。だから銘柄を出さない。

## データスキーマ

毎朝ルーチンが `data/enriched-coffee-news.json`（ファイル名は歴史的なもの。中身は今日の抽出メモ）に書く:

```jsonc
{
  "date": "YYYY-MM-DD",          // JST の今日
  "format": "brew-lesson",       // これ以外は無い
  "trial": "coffee-trial-2-brew-basics",
  "lesson": {
    "pillar": "temp",            // PILLARS のキー
    "method": "v60",             // METHODS のキー
    "scene": "hot",              // hot | iced（cold-brew は iced 必須）
    "hook": "湯温を3度下げる",      // ≤16 字。今日の問い（1 枚目の大見出し）
    "topic": "苦味が引いて酸が立つ", // ≤18 字。答えを 1 行で
    "why": "温度が高いほど苦味成分が多く溶ける", // ≤30 字。理屈
    "numbers": { "dose_g": 15, "water_g": 240, "temp_c": 88, "grind": "中細", "time": "2:30" },
    "steps": [ { "time": "0:00", "action": "蒸らす", "pour_to_g": 45 } ],  // 1〜5 件
    "taste": { "notes": ["軽い苦味"], "summary": "後味がすっきりする", "acidity": 4, "sweetness": 3, "body": 2 },
    "tips": [ { "problem": "酸っぱい時", "fix": "湯温を92度に戻す" } ],      // 2〜3 件
    "sources": ["https://…"],    // 任意。出典があるときだけ
    "narration": { "title": "…", "numbers": "…", "steps": "…", "taste": "…", "tips": "…", "cta": "…" } // 任意
  }
}
```

検証ルール（`scripts/content-format.mjs`・すべて機械チェック）:

- 文字数上限は `LIMITS`（1080×1920 のレイアウト由来。本文は 30px を下回らせない = 縮めずに短く書く）
- 数値は `METHOD_BOUNDS` の範囲内（抽出法ごとの比率・時間・湯量）。`steps` の時刻は昇順で `numbers.time` 以内、`pour_to_g` は増加し、最後は `numbers.water_g` ±2
- 水出しは食品安全: 冷蔵庫（1〜10℃）で 6〜24 時間、手順に「冷蔵庫」の語が要る。常温・一晩・日単位は全テキストで NG（`unsafeSteepReason`）
- URL・`@`・`#`・不可視文字は全テキストで NG（`unsafeTextReason`。ルーチンの PR は人間レビュー無しで main に入るため）
- ナレーション合計 260 字以内（IG Reels は 60 秒超を弾く）
- **ブランドガード**（上の NG 節）
- `beanId` を書いたら即エラー

### 常備ネタ帳（`data/brew-lessons.json`）

ルーチンが原稿を出せなかった朝の差し替え用。**17 本**入っていて 8 つの柱を全部カバーしており、日付でローテーションし、前日と同じ柱・抽出法は避ける。だから休んだ日も汎用知識が出る（豆の話には決して戻らない）。追加・修正は人間の PR で。

### 豆マスタ（`data/coffee-lineup.json`）

**コンテンツ生成の入力ではない。** 販促フェーズに戻す日のために残してあるのと、ブランドガードが「出してはいけない名前」を自動で拾うために読むだけ。

## 数値の根拠

湯温・比率・抽出率の目安は SCA（Specialty Coffee Association）の抽出基準に合わせている: 湯温は粉に触れる時点で 92℃ 以上・96℃ を超えない、標準の比率は 55 g / 1,000 g、良いとされる抽出率は 18〜22%（SCA Standard 310-2021 "Home Coffee Brewers", sca.coffee）。動画は家庭の器具向けにこれより広い範囲（`METHOD_BOUNDS`）を許すが、「基準はどこか」を外さない。
