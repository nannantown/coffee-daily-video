### 判定窓・経過日・次の判定日と集計

d = 今日 − S（日数。日付はすべて JST）

| 条件 | 経過日 | 判定窓 | 次の判定日 |
|---|---|---|---|
| d < 0 | 未開始（S が未来の日付 = 台帳の書き間違い。前の試行の行・前回モード・方針をそのまま続け、レポートの「注意」行に書く） | — | — |
| d ≥ 14 かつ d が 14 の倍数 | **判定日** | (今日 − 14)..(今日 − 1) | 今日 + 14 |
| それ以外 | Day (d mod 14 + 1) / 14 | max(F, 今日 − 13)..今日 | S + 14 × (floor(d / 14) + 1) |

例（S = 2026-09-14）: 09-15 は Day 2 / 14・判定窓 09-02..09-15・次の判定日 09-28。09-28 は判定日（判定窓 09-14..09-27）。09-29 は Day 2 / 14（次の判定日 10-12）。

**毎朝の集計は `node scripts/pdca-summary.mjs`**。上の表・下の判定指標・閾値・モードの決め方（前回レポートのモード列の引き継ぎ、判定日と遅延判定）を実装しており、レポート冒頭の節をそのまま出す（テスト: `scripts/pdca-summary.test.mjs`）。正本と同じ定義の jq 版（突き合わせ用）は、S と F を台帳の値にすれば、今日の日付から判定窓・経過日・次の判定日・判定指標をまとめて出す（日付を手で書き換えない）。IG と YT で S / F が違うときは行ごとに実行し、該当する側の数字を使う。

```bash
TODAY=$(TZ=Asia/Tokyo date +%Y-%m-%d); S=2026-09-14; F=2026-04-20
jq -r --arg today "$TODAY" --arg s "$S" --arg f "$F" '
  def day: strptime("%Y-%m-%d") | mktime / 86400 | floor;
  def ymd: . * 86400 | strftime("%Y-%m-%d");
  def median: sort | if length==0 then null elif length%2==1 then .[(length/2|floor)] else ((.[length/2-1]+.[length/2])/2) end;
  ($today|day) as $t | ($s|day) as $sd | ($f|day) as $fd | ($t - $sd) as $d
  | if $d < 0 then "today=\($today) status=未開始"
    else
      (if ($d >= 14 and ($d % 14) == 0) then {status:"判定日", from:($t-14|ymd), to:($t-1|ymd), next:($t+14|ymd)}
       else {status:"Day \(($d % 14)+1) / 14", from:([$fd, $t-13]|max|ymd), to:$today, next:($sd + 14*((($d/14)|floor)+1)|ymd)} end) as $w
      | [.videos[] | select(.date >= $w.from and .date <= $w.to)] as $v
      | ($v | map(select(.stats.updatedAt != null) | (.stats.views // 0))) as $yt
      | ($v | map(select(.instagram != null and .instagram.views != null) | .instagram)) as $ig
      | "today=\($today) status=\($w.status) window=\($w.from)..\($w.to) next_judgment=\($w.next) posts=\($v|length)",
        "YT views median=\($yt|median) (n=\($yt|length))",
        "IG views median=\($ig|map(.views)|median) saved_sum=\($ig|map(.saved // 0)|add // 0) (n=\($ig|length))"
    end
' data/performance-history.json
```

- 過去の判定日 J の判定（遅延判定）を出すときは、`TODAY` に J を入れて実行する（status=判定日、判定窓 (J − 14)..(J − 1) になる）
- jq の日付関数が使えない環境では、上の表どおりに `date -d` で判定窓を出し、同じ条件（YT は `stats.updatedAt` あり、IG は `instagram.views` あり）で中央値と合計を出す

### 判定指標

- **IG**: 判定窓の `instagram.views` の**中央値**と、`instagram.saved` の**合計**（別々の 2 指標で、足さない）。`instagram` か `instagram.views` が null の回は除外
- **YT**: 判定窓の `stats.views` の**中央値**。`stats.updatedAt` が null の回は除外
- n は IG / YT で別々に数える。**n < 7 なら判定保留**。IG と YT の数字を足したり平均したりしない
- 朝ルーチンの時点では当日分は未投稿で、前日分も統計・insights が未取得のことが多い（除外されるので、通常日の n は最大 12 前後）

### モードの決め方（毎朝、アカウントごと）

モードは `通常` / `切替候補` / `配信死亡モード` の 3 つ。**モードが変わるのは判定日（と遅延判定）だけ**で、それ以外の日は前回モードを続ける（行ったり来たりを防ぐ）。

1. **前回モード** = `docs/pdca/` の `YYYY-MM-DD.md` のうち、**今日より前の日付で「ジャンル試行の状態」表のモード列が読める最新のもの**のモード列。表の無いレポート（「未導入」の 2 行だけ・ルーチンの失敗など）は飛ばして、さらに前の日付を見る。1 本も無いときだけ、上の台帳の「導入時の判定」（配信死亡 → `配信死亡モード（2026-09-14〜）`）。**新しい試行が始まっても前回モードを引き継ぐ**（新しい試行の最初の判定日に、その試行の数字で判定し直す）
2. **遅延判定**: 今日より前の直近の判定日 J について、J 以降の日付のレポートに「ジャンル判定」節が無ければ（ルーチンの失敗・導入の遅れなど）、今日まず J の判定を窓 (J − 14)..(J − 1) で出し、3. の判定日と同じ扱いでモードを決め直してから今日の分に進む。判定日は S + 14k（k ≥ 1）だけで、S 当日（2026-09-14 の「導入時の判定」）は判定日ではないので、遅延判定の対象にしない
3. **決定**:
   - **今日が判定日（または遅延判定）** → 判定値どおり: 配信死亡 → `配信死亡モード`（前回から続くなら宣言日はそのまま、新しく入るなら宣言日 = その判定日）/ 切替候補 → `切替候補` / 続行 → `通常` / 判定保留（n < 7）→ 前回モードのまま
   - **それ以外の日** → 前回モードのまま。今日の判定値が配信死亡なのにモードが `配信死亡モード` でないときは、レポートに「注意」行を書く（モードの変更は次の判定日）

### 通常・切替候補のときの日次 PDCA

- 豆・抽出法・切り口の比較は、**型の初回投稿日 F 以降の回だけ**で行う（新しい型の序盤に古い型の数字を混ぜない。回数が少なければローテーション寄りでよい）。比較に使う「直近 14 日」は判定窓とは別で、**今日より前の 14 日**（今日 − 14..今日 − 1）
- 比較は**アカウントごと**（IG は保存数が主指標、YT は views を別に参考。合算スコアを作らない）。「伸びた軸を続ける」判断は、配信死亡モードでないアカウントの数字から行う
- 切替候補のアカウントは、判定日に次ジャンル候補を 2〜3 案出す（このリポの制約を守る）。日々の最適化は通常どおり続ける

### 配信死亡モード中の日次 PDCA

1. **性能データで切り口を最適化しない**: 配信死亡モードのアカウントの数字で、豆・抽出法・切り口の TOP/WORST 比較や「伸びた軸を続ける」判断をしない（0 と 1 を比べても何も分からない）
   - **2 アカウントとも配信死亡モード** → 豆・抽出法・切り口は**性能データで選ばない**。`pdca-summary.mjs` の「ローテーション」で**直近 14 日の使用回数が少ないもの**から、曜日の型（月〜土 recipe / 日 news-top5）と「同じ豆・抽出法を 2 日連続にしない」を守って選ぶ（同数なら豆マスタ・抽出法一覧の上から。日曜の `discovery.method` も直近 14 日の使用回数が少ないものから、同数なら下の「Discovery Methods」表の上から）。軸別の表は参考表示のみ
   - **片方だけ配信死亡モード** → 比較は**生きている側のアカウントの指標だけ**で行う。生きている側も判定窓の n < 7 で指標が使えない日は、2 アカウントとも配信死亡モードのときと同じ選び方（ローテーション）をする
2. **提案は構造実験だけ**: タイトル個別化 / 型変更 / ジャンル変更。各提案に「何を変えるか / 何で測るか / 14 日後の合格ライン」を書く。合格ラインの既定は上の閾値表の「続行」域（IG: views 中央値 ≥ 50 または保存合計 ≥ 5 / YT: views 中央値 ≥ 20）で、配信死亡を抜けるだけの線を合格にしない。同じ動画を IG と YT に出しているので、動画そのものを変える提案（型変更・ジャンル変更）は `IG / YT 共通` の 1 行にまとめてよい。片方だけの変更（タイトル個別化など）はアカウント別に書く
3. **提案はレポートに書くだけ**: 当日の原稿・タイトル・`data/enriched-coffee-news.json` には反映しない（型・スキーマは下の「データスキーマ」どおり。反映すると動画生成が失敗しうる）。次ジャンル候補や構造実験は手持ちのデータと知識で短く書き、Web 調査に時間を使わない（原稿と JSON の書き出しを優先する）
4. **新しい試行が走っている間**（試行 #1 以降で、まだ最初の判定日前）は、「構造実験の提案」節に `実行中: 試行 #n（<ジャンル / 型>）Day N / 14` とだけ書き、追加の提案は判定日まで控える（変数を増やさない）。試行 #1 が main に入っていてまだ新型の初回投稿が無い間も同じで、`準備中: 試行 #1（<ジャンル / 型>）` とだけ書き、同じ案を毎朝書き直したり別案を足したりしない（`pdca-summary.mjs` がこの行を出す）
5. **このリポの制約**: ジャンル・型は変えてよいが、**販促（自家焙煎豆の購入への導線）の目的は維持**。候補は豆の購入に繋がる型に限る（例: レシピ、焙煎の裏側、産地×味の比較、商品ができるまで）
6. **投稿は止めない**。原稿の作成は通常どおり。型の切替は人間が決めて PR で入れる

- 1 枚目で数値が全部見える（AI Trend Daily の「数字で並べる」型に寄せる）。IG のサムネイルは 1.5 秒の位置（1 枚目が出そろった状態）から取る
- 写真素材は後から足す前提で、まず文字だけ。タイポ: 本文 30px 以上 / ラベルは solid pill（不透明の塗り + 白文字、色は枠線で持つ）/ 線・バーの色とテキストの色を一致させない / フォントは既存の Noto Sans CJK JP
- ナレーションは補助（カードだけで完結するので字幕は出さない）。合計 230 文字目安、上限 260。60 秒を超えそうなら話速を上げ、それでも長ければ短い自動読み上げ文に差し替える。無音の動画は投稿前に止める

## ペルソナ（優先順）

### Primary: 家で淹れる趣味層
- 既にコーヒー器具（ドリッパー、ミル）を所有
- 1 袋 ¥1,500〜¥3,000 に抵抗がない
- 産地・精製方法・ロースト日などの情報で買う豆を決める
- **失敗した淹れ方のリカバリに興味がある**（→ 悩み別のコツ）
- **この層を取れなければ事業成立しない**

### Secondary: 開業したての小規模カフェ店主
- 卸先として直接的な収益
- 1 店舗が決まると月5〜15kg の安定需要
- SNS は広告ではなく「焙煎所を知ってもらう信頼シグナル」として機能（→ 抽出レシピの具体性が信頼になる）

### Tertiary: ギフト需要
- おしゃれなビン/パッケージが意思決定に効く
- 父の日、誕生日、開業祝いなど季節キャンペーンで拾う

## 差別化ポイント

1. **焙煎した本人が出す数値つきレシピ** — 豆ごとの湯温・挽き目・比率は焙煎所にしか出せない一次情報
2. **毎回、実際に買える自社豆で淹れる** — レシピがそのまま商品カタログになる
3. **ビン・パッケージの意匠** — 贈答にそのまま使える

## PDCA で比べる軸

`record-upload.mjs` が `performance-history.json` の `content` に記録し、`pdca-summary.mjs` が IG 保存数で並べる（上の「ジャンル実験」節のモードに従って使う）。

| 軸 | 値 | `content` のキー |
|---|---|---|
| 豆 | 豆マスタの id | `beanId` / `beanName` |
| 抽出法 | V60 / カリタウェーブ / ORIGAMI / ケメックス / クレバー / フレンチプレス / エアロプレス / 水出し / マキネッタ | `method` |
| 切り口 | 悩み起点 / 季節 / 豆の個性 / 器具 / 名レシピ応用 | `angle` |
| 温度帯 | ホット / アイス | `scene` |
| 悩み | コツカードの「〜時」 | `tipProblems` |
| 型 | レシピ / ニュース TOP5 / 代替（標準レシピ） | `format` / `fallback` |

ローテーション: 同じ豆・同じ抽出法を 2 日連続で使わない。7 日で全ラインナップを 1 回以上。暑い時期のアイスは週 2 回まで。

## 日曜ニュース TOP5 の探索方針

### 英語優先原則

**英語ソースを先に見る**。日本語メディアは英語を翻訳する形で 1〜3 日遅れる。先に英語で拾い、日本の家で淹れる人・豆を買う人に効く順（価格・供給・産地・トレンド）で 5 本に絞る。

### 推奨ソース（シード）

**英語（優先）**: Perfect Daily Grind / Daily Coffee News (Roast Magazine) / SCA News / Bloomberg・Reuters（Arabica Futures, Coffee C）/ World Coffee Research / Global Coffee Report / World Coffee Portal / Reddit r/Coffee, r/roasting

**日本語（バックアップ）**: SCAJ 公式 / 業界誌（カフェ＆レストラン、Coffee magazine JP）/ X の日本語バリスタ界隈

### Discovery Methods（`discovery.method`）

| タグ | 説明 |
|---|---|
| `news-en` | 英語の業界メディア・ニュースサイト |
| `news-ja` | 日本語の業界メディア |
| `market-data` | 商品市況、為替、指標データ |
| `official-src` | 産地機関、協会、WCR 等の公式発信 |
| `social-en` | Reddit / X（英語）のコミュニティ話題 |
| `social-ja` | X 日本語バリスタ・焙煎士界隈 |
| `trends` | Google Trends, X Trending |
| `expert-blog` | 業界有名人の個人発信・ブログ |

## NG パターン

| NG | 理由 |
|---|---|
| **数値が物理的に合わないレシピ**（最後の注湯量 ≠ お湯の量、常識外の比率、アイスなのに氷の量なし） | 保存される実用性の根幹。`validate-content.mjs` が機械チェック |
| **ラインナップ外の豆を使う** | 販促が目的。マスタにない豆は検証で弾かれ、標準レシピに差し替わる |
| **ラベル表記と矛盾するフレーバー** | 買った人の期待を裏切る |
| 出典のない「有名レシピ」 | `angle: expert` は `recipe.sources` の URL が必須（検証で弾く） |
| 健康効果・医療的な断定、根拠のない最上級 | 信用毀損 |
| 「コーヒーあるある」「コーヒー雑学」 | 通りすがりが集まるが、豆を買う層ではない |
| 「モーニングルーティン」系 | 差別化不能、競合だらけ |
| 「インスタント vs ドリップ」的な初心者解説 | ターゲット層には幼稚に映る |
| **非公開 EC への URL 誘導** | COMING SOON の画面で止まり失望させる。`ecPublic: true` になるまでは DM 導線 |
| 1 週間以上前のニュース（日曜 TOP5） | 鮮度が命。`freshness_hours > 168` は NG |
| 出典不明ニュース（日曜 TOP5） | 信用毀損。項目ごとに URL を必ず記録 |


## KPI ダッシュボード

- **主指標: IG 保存数 / 動画**（保存率 = 保存 ÷ reach）
- IG views 中央値・shares・reach（`performance-history.json` の `instagram.*`）
- 軸別（抽出法 / 豆 / 切り口）の IG 保存平均（`scripts/pdca-summary.mjs`）
- DM での購入・卸の問い合わせ数（手動記録）
- EC 公開後: EC 遷移数（UTM）/ 注文件数 / 平均注文単価 / 定期便契約率
- 参考: YT views（IG と合算しない）

### performance-history.json の指標

| キー | 取得元 | 更新 |
|---|---|---|
| `stats.views` / `likes` / `comments` | YouTube Data API v3 | `fetch-stats.mjs`（直近 14 日） |
| `instagram.mediaId` | 投稿時に `upload-instagram.mjs` → `record-upload.mjs` が記録。無い回は `fetch-stats.mjs` が IG 投稿一覧と JST 投稿日で突き合わせて復元 | 投稿時 / 初回取得時 |
| `instagram.views` / `reach` / `likes` / `comments` / `shares` / `saved` | Instagram Graph API `/{ig-media-id}/insights`（`plays` は廃止済みのため `views` を使用） | `fetch-stats.mjs`（直近 14 日 + 未取得の回） |
| `content` | `record-upload.mjs`（`format` / `trial` / `fallback` / `beanId` / `method` / `angle` / `scene` / `tipProblems`、ニュースは `headlines`）。旧型ニュースの回は無し | 投稿時 |

IG insights は最大 48 時間遅れる。前日・前々日の IG 値は暫定として比較から外す（`pdca-summary.mjs` が「（暫定）」を付ける）。手動で更新だけしたいときは `gh workflow run fetch-stats.yml`（動画生成・投稿はしない）。

## データスキーマ（`data/enriched-coffee-news.json`）

ファイル名は横断 PDCA ルーチンと `record-upload.mjs` が読むので据え置き、`format` で型を切り替える。フィールドと文字数上限の正本は `scripts/content-format.mjs`、ルーチン向けの書き方は [routine-prompt.md](routine-prompt.md)。**完全な見本は `data/samples/recipe.sample.json` / `data/samples/news-top5.sample.json`**（下は構造だけの抜粋で、このままでは検証を通らない）。

```json
{
  "date": "2026-09-15",
  "format": "recipe",
  "trial": "coffee-trial-1-recipe-card",
  "recipe": {
    "beanId": "ethiopia-yirgacheffe-kochere",
    "method": "v60",
    "scene": "hot",
    "angle": "trouble",
    "hook": "浅煎りが酸っぱい人のV60",
    "numbers": { "dose_g": 15, "water_g": 225, "temp_c": 93, "grind": "中細挽き", "time": "2:30" },
    "steps": ["…（1〜5 件、最後の pour_to_g = water_g）"],
    "taste": { "notes": ["レモン"], "summary": "酸味が甘さに変わる一杯", "acidity": 3, "sweetness": 4, "body": 2 },
    "tips": ["…（2〜3 件）"],
    "narration": { "title": "…", "numbers": "…", "steps": "…", "taste": "…", "tips": "…", "cta": "…" }
  }
}
```

`format` の無い JSON（旧型ニュース）は、当日付で**旧型の必須キー**（`discovery.method`、`articles[]` の `rank` / `title` / `description` / `narration`）が揃っているときだけ従来のニュース解説として描画される（切り戻し用）。揃っていない JSON や、`recipe` / `newsTop5` を持つのに `format` だけ書き忘れた JSON は旧型扱いにせず、検証 NG → 標準レシピになる。

朝ルーチンは Web を読んで書き、その PR は人の目を通らずに自動マージされるので、**原稿は信用しない入力として検証する**:

- 水出しは食品衛生のため **冷蔵庫（1〜10℃）で 6〜24 時間**、手順に「冷蔵庫」が必須。さらに**すべてのレシピ**のテキスト欄を NFKC 正規化してから、「常温で」「室温のまま」「冷蔵庫に入れない / 冷蔵庫でなく」、日数（2日・一日半・3 days）、24 時間を超える時間（30時間・48h）を NG、「常温」「室温」「キッチン」「置いたまま」「一晩」は同じ文に「冷蔵」が無ければ NG（水出し以外のレシピに水出しの手順が混ざっても同じ）
- テキスト欄（フック・手順・味・コツ・ナレーション・見出し・要約・出典名）に URL・ドメイン名・`@`・`#`・改行・見えない文字（ゼロ幅・向き制御など）があれば NG（全角の `＠` `＃` などは NFKC 正規化してから判定）
- ニュースの `url` と `discovery.sources` は、`data/news-sources.json` に載せたニュースサイトのホスト（サブドメイン可）の `https://` URL だけ（ユーザー名・パスワード付き、ポート指定、IP アドレスは NG）。`url` はさらに `discovery.sources` のどれかと一致すること。一覧の追加・削除は PR で
- 確定済み（confirmed）の豆が 1 つも無い間: 月〜土の朝ルーチンは原稿を書かずレポートだけをマージ（パイプラインは豆を紹介しない旧型の豆知識で投稿）、日曜ニュースは「月〜土は今日の一杯レシピ」と言わない
- 抽出法ごとの安全枠（比率・総時間・湯量）の外は NG（範囲は `docs/routine-prompt.md` 2a-4 と `scripts/content-format.mjs` の `METHOD_BOUNDS`）
- 代替投稿（標準レシピ・旧型の豆知識）になった日は、Actions の警告と実行サマリーに理由が出る

## 検証とロールバック

- 検証（投稿しない）: `gh workflow run daily-video.yml --ref <branch> -f sample=recipe`（`news-top5` / `fallback` / `today` も可）。main 以外の ref、`dry_run=true`、`sample` が `today` 以外のときは常に検証モードで、動画・カバー・キャプション・カード画像を artifact に出す。ローカルは `DRY_RUN=true node scripts/pipeline.mjs --content=data/samples/recipe.sample.json`
- 投稿した動画のキャプションは GitHub Release に `coffee-YYYYMMDD-captions.json` として残り、再投稿ワークフローはそれを使う（レシピの数値が動画とずれない）
- 試行を打ち切る場合: `docs/routine-prompt.md` の Routine Prompt を旧型の JSON を書く内容に戻せば、パイプラインは旧型の必須キーが揃った `format` の無い JSON を旧ニュース解説として描画する
