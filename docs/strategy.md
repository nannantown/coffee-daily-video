### 判定窓・経過日・次の判定日と集計コマンド

d = 今日 − S（日数。日付はすべて JST）

| 条件 | 経過日 | 判定窓 | 次の判定日 |
|---|---|---|---|
| d < 0 | 未開始（前の試行の行・モード・method 方針をそのまま続ける） | — | — |
| d ≥ 14 かつ d が 14 の倍数 | **判定日** | (今日 − 14)..(今日 − 1) | 今日 + 14 |
| それ以外 | Day (d mod 14 + 1) / 14 | max(F, 今日 − 13)..今日 | S + 14 × (floor(d / 14) + 1) |

例（S = 2026-09-14）: 09-15 は Day 2 / 14・判定窓 09-02..09-15・次の判定日 09-28。09-28 は判定日（判定窓 09-14..09-27）。09-29 は Day 2 / 14（次の判定日 10-12）。

下のコマンドは、S と F を台帳の値にすれば、今日の日付から判定窓・経過日・次の判定日・判定指標をまとめて出す（日付を手で書き換えない）。IG と YT で S / F が違うときは行ごとに実行し、該当する側の数字を使う。

```bash
TODAY=$(TZ=Asia/Tokyo date +%Y-%m-%d); S=2026-09-14; F=2026-04-20
jq -r --arg today "$TODAY" --arg s "$S" --arg f "$F" '
  def day: strptime("%Y-%m-%d") | mktime / 86400 | floor;
  def ymd: . * 86400 | strftime("%Y-%m-%d");
  def median: sort | if length==0 then null elif length%2==1 then .[(length/2|floor)] else ((.[length/2-1]+.[length/2])/2) end;
  ($today|day) as $t | ($s|day) as $sd | ($f|day) as $fd | ($t - $sd) as $d
  | if $d < 0 then "today=\($today) status=未開始"
    else
      (if ($d >= 14 and ($d % 14) == 0) then {status:"判定日", from:($t-14|ymd), to:($t-1|ymd), next:($t+14|ymd)}
       else {status:"Day \(($d % 14)+1) / 14", from:([$fd, $t-13]|max|ymd), to:$today, next:($sd + 14*((($d/14)|floor)+1)|ymd)} end) as $w
      | [.videos[] | select(.date >= $w.from and .date <= $w.to)] as $v
      | ($v | map(select(.stats.updatedAt != null) | (.stats.views // 0))) as $yt
      | ($v | map(select(.instagram != null and .instagram.views != null) | .instagram)) as $ig
      | "today=\($today) status=\($w.status) window=\($w.from)..\($w.to) next_judgment=\($w.next) posts=\($v|length)",
        "YT views median=\($yt|median) (n=\($yt|length))",
        "IG views median=\($ig|map(.views)|median) saved_sum=\($ig|map(.saved // 0)|add // 0) (n=\($ig|length))"
    end
' data/performance-history.json
```

- 過去の判定日 J の判定（遅延判定）を出すときは、`TODAY` に J を入れて実行する（status=判定日、判定窓 (J − 14)..(J − 1) になる）
- jq の日付関数が使えない環境では、上の表どおりに `date -d` で判定窓を出し、同じ条件（YT は `stats.updatedAt` あり、IG は `instagram.views` あり）で中央値と合計を出す

### 判定指標

- **IG**: 判定窓の `instagram.views` の**中央値**と、`instagram.saved` の**合計**（別々の 2 指標で、足さない）。`instagram` か `instagram.views` が null の回は除外
- **YT**: 判定窓の `stats.views` の**中央値**。`stats.updatedAt` が null の回は除外
- n は IG / YT で別々に数える。**n < 7 なら判定保留**。IG と YT の数字を足したり平均したりしない
- 朝ルーチンの時点では当日分は未投稿で、前日分も統計・insights が未取得のことが多い（除外されるので、通常日の n は最大 12 前後）

### モードの決め方（毎朝、アカウントごと）

モードは `通常` / `切替候補` / `配信死亡モード` の 3 つ。**モードが変わるのは判定日（と遅延判定）だけ**で、それ以外の日は前回モードを続ける（行ったり来たりを防ぐ）。

1. **前回モード** = `docs/pdca/` の `YYYY-MM-DD.md` のうち**今日より前の日付で最新のもの**の「ジャンル試行の状態」表のモード列。表が無い・モード列が読めない（「未導入」の 1 行だけ等）ときは、上の台帳の「導入時の判定」（配信死亡 → `配信死亡モード（2026-09-14〜）`）。**新しい試行が始まっても前回モードを引き継ぐ**（新しい試行の最初の判定日に、その試行の数字で判定し直す）
2. **遅延判定**: 今日より前の直近の判定日 J について、J 以降の日付のレポートに「ジャンル判定」節が無ければ（ルーチンの失敗・導入の遅れなど）、今日まず J の判定を窓 (J − 14)..(J − 1) で出し、3. の判定日と同じ扱いでモードを決め直してから今日の分に進む
3. **決定**:
   - **今日が判定日（または遅延判定）** → 判定値どおり: 配信死亡 → `配信死亡モード`（前回から続くなら宣言日はそのまま、新しく入るなら宣言日 = その判定日）/ 切替候補 → `切替候補` / 続行 → `通常` / 判定保留（n < 7）→ 前回モードのまま
   - **それ以外の日** → 前回モードのまま。今日の判定値が配信死亡なのにモードが `配信死亡モード` でないときは、レポートに「注意」行を書く（モードの変更は次の判定日）

### 通常・切替候補のときの日次 PDCA（Meta PDCA の補足）

- method の比較・80/20 は、**型の初回投稿日 F 以降の回だけ**で行う（新しい型の序盤に古い型の数字を混ぜない。回数が少なければ Explore 寄りでよい）
- method の順位は**アカウントごとに**付ける（IG の TOP 3 と YT の TOP 3 を別々に出し、合算スコアを作らない）。80/20 の exploit 候補は、配信死亡モードでないアカウントの TOP 3 から選ぶ
- 切替候補のアカウントは、判定日に次ジャンル候補を 2〜3 案出す（このリポの制約を守る）。日々の method 最適化は通常どおり続ける

### 配信死亡モード中の日次 PDCA

1. **method 切り口の最適化を止める**: 配信死亡モードのアカウントの数字で method の TOP/WORST 比較・Method 提案・80/20 選定・WORST method の凍結をしない（0 と 1 を比べても何も分からない）
   - **2 アカウントとも配信死亡モード** → method は**性能データで選ばない**。曜日の型（平日/週末）・「直近 2 日と同じ method を連続で選ばない」・NG パターンを満たす method のうち、**直近 14 日の使用回数が少ないもの**を選ぶ（同数なら下の「Discovery Methods」表の上から）。WORST method の凍結はすべて解除して扱う。レポートの「Method 提案」節は「配信死亡モードのため省略」と 1 行だけ書く。method 別テーブルは参考表示のみ
   - **片方だけ配信死亡モード** → method の比較と 80/20 は**生きている側のアカウントの指標だけ**で行う
2. **提案は構造実験だけ**: タイトル個別化 / 型変更 / ジャンル変更。各提案に「何を変えるか / 何で測るか / 14 日後の合格ライン」を書く。同じ動画を IG と YT に出しているので、動画そのものを変える提案（型変更・ジャンル変更）は `IG / YT 共通` の 1 行にまとめてよい。片方だけの変更（タイトル個別化など）はアカウント別に書く
3. **提案はレポートに書くだけ**: 当日の原稿・タイトル・`data/enriched-coffee-news.json` には反映しない（型・スキーマ・必須フィールドは従来どおり。反映すると動画生成が失敗しうる）。次ジャンル候補や構造実験は手持ちのデータと知識で短く書き、Web 調査に時間を使わない（原稿と JSON の書き出しを優先する）
4. **新しい試行が走っている間**（試行 # が #1 以降で、まだ最初の判定日前）は、「構造実験の提案」節に `実行中: 試行 #n（<ジャンル / 型>）Day N / 14` と書き、追加の提案は判定日まで控える（変数を増やさない）
5. **このリポの制約**: ジャンル・型は変えてよいが、**販促（自家焙煎豆の購入への導線）の目的は維持**。候補は豆の購入に繋がる型に限る（例: レシピ、焙煎の裏側、産地×味の比較、商品ができるまで）
6. **投稿は止めない**。ネタ調査・原稿生成は通常どおり。型の切替は人間が決めて PR で入れる

## 運用フォーマット: ニュース中心

**「毎朝チェックしないと乗り遅れる」FOMO を作る**ために、コンテンツはニュース性を主軸とする。エバーグリーン豆知識は単体では習慣化されにくい（いつ見てもいい = 見ない）。

|---|---|---|
| 月〜金 | **毎朝のコーヒーニュース**（市況、産地、業界動向） | Primary |
| 土・日 | **エバーグリーン深掘り**（焙煎、産地、抽出） | Secondary |

週末エバーグリーンは「今週出たニュースの背景を深く知る」接続を意識する（ニュース駆動ニュース系情報として残る）。

## ペルソナ（優先順）

### Primary: 家で淹れる趣味層
- 既にコーヒー器具（ドリッパー、ミル）を所有
- 1 袋 ¥1,500〜¥3,000 に抵抗がない
- 産地・精製方法・ロースト日などの情報で買う豆を決める
- 失敗した淹れ方のリカバリに興味がある
- **この層を取れなければ事業成立しない**

### Secondary: 開業したての小規模カフェ店主
- 卸先として直接的な収益
- 1 店舗が決まると月5〜15kg の安定需要
- SNS は広告ではなく「焙煎所を知ってもらう信頼シグナル」として機能

### Tertiary: ギフト需要
- おしゃれなビン/パッケージが意思決定に効く
- 父の日、誕生日、開業祝いなど季節キャンペーンで拾う

## 差別化ポイント

1. **スペシャリティにこだわる知識量** — 焙煎士が一次情報を発信

3. **SNS で焙煎士の顔が見える** — ECの店主が誰かわかる安心感

## 探索方針（Discovery Strategy）

### 英語優先原則

**英語ソースを先に見る**。日本語メディアは英語を翻訳する形で1日遅れる。先に英語で拾い、日本語視聴者向けに翻訳・噛み砕く方が速報性・独自性・視聴者への価値で勝る。
日本語ソースは補完（英語で見つからないドメスティック情報や地域事情用）。

### 推奨ソース（シード）

**英語（優先）**:
- Perfect Daily Grind — 業界トピックの深堀り
- Daily Coffee News (Roast Magazine) — 業界ニュース
- SCA News (sca.coffee) — スペシャリティ協会公式
- Bloomberg / Reuters — 商品市況（Arabica Futures, Coffee C）
- World Coffee Research — 研究・品種
- Global Coffee Report — 国際動向
- Reddit r/Coffee, r/roasting — コミュニティ声

**日本語（バックアップ）**:
- SCAJ（日本スペシャルティコーヒー協会）公式発信
- 業界誌（カフェ＆レストラン、Coffee magazine JP）
- X（Twitter）日本語バリスタ界隈

### Discovery Methods（カテゴリタグ）

| タグ | 説明 |
|---|---|
| `news-en` | 英語の業界メディア・ニュースサイト |
| `news-ja` | 日本語の業界メディア |
| `market-data` | 商品市況、為替、指標データ |
| `official-src` | 産地機関、協会、WCR 等の公式発信 |
| `social-en` | Reddit / X（英語）のコミュニティ話題 |
| `social-ja` | X 日本語バリスタ・焙煎士界隈 |
| `trends` | Google Trends, X Trending |
| `expert-blog` | 業界有名人の個人発信・ブログ |

### 80/20 Exploit/Explore

- 過去14日で視聴率上位3位の method は 80% の頻度で使う（exploit）
- 残り 20% は**新しい method を試す**（explore）。探せば新カテゴリが見つかるはず
- Explore でヒットした method は次サイクルで exploit 側に昇格

### Meta PDCA（探し方の PDCA）

> 冒頭の「ジャンル実験」節が優先する。以下の method 比較・80/20 は**型の初回投稿日 F 以降の回だけ**で、**アカウントごとに**（IG と YT を合算せず）行う。**配信死亡モードのアカウントの数字では method 比較・80/20・凍結をしない**（2 アカウントとも配信死亡モードなら性能データで method を選ばない。片方だけなら生きている側の指標だけを使う）。

毎日のルーチンで以下を分析:

1. 直近 14 日の `performance-history.json` から **method → 平均 views** テーブルを作成
   - YouTube は `stats.views`、Instagram Reels は `instagram.views`（加えて `reach` / `shares` / `saved`）を**別列で並べる**。両者を合算しない（計測定義が違う）
   - `instagram` が `null` の動画は IG 投稿と突き合わせ不能だった回。IG 側の平均から除外する
   - IG insights は最大 48 時間遅れる。前日・当日分の IG 値は暫定として扱う
2. TOP 3 / WORST 3 method を特定
3. 「今日はどの method で探すか」を 80/20 ルールで決める
4. 新しい method のアイデアがあれば PDCA レポートの「Method 提案」セクションに記録
5. **WORST method は 2 週連続なら一旦凍結**（リストから外す、別 method 優先）

## NG パターン

| NG | 理由 |
|---|---|
| 「コーヒーあるある」「コーヒー雑学」 | 通りすがりが集まるが、豆を買う層ではない |
| 「モーニングルーティン」系 | 差別化不能、競合だらけ |
| 「インスタント vs ドリップ」的な初心者解説 | ターゲット層には幼稚に映る |
| EC が未完成の段階での強い購買 CTA | 失望させる。まず「焙煎所フォローして待つ価値」を積む |
| 産地タグの使い回し（水の話で "産地" など） | 動的ラベルを使う |
| **1週間以上前のニュースを新着扱い** | 鮮度が命。`freshness_hours > 168` は原則 NG |
| **出典不明ニュース** | 信用毀損。ソース URL を必ず記録・明示する |

### performance-history.json の指標

| キー | 取得元 | 更新 |
|---|---|---|
| `stats.views` / `likes` / `comments` | YouTube Data API v3 | `fetch-stats.mjs`（直近 14 日） |
| `instagram.mediaId` | 投稿時に `upload-instagram.mjs` → `record-upload.mjs` が記録。無い回は `fetch-stats.mjs` が IG 投稿一覧と JST 投稿日で突き合わせて復元 | 投稿時 / 初回取得時 |
| `instagram.views` / `reach` / `likes` / `comments` / `shares` / `saved` | Instagram Graph API `/{ig-media-id}/insights`（`plays` は廃止済みのため `views` を使用） | `fetch-stats.mjs`（直近 14 日 + 未取得の回） |

手動で更新だけしたいときは `gh workflow run fetch-stats.yml`（動画生成・投稿はしない）。

## データスキーマ拡張（enriched-coffee-news.json）

ニュース駆動 + Discovery 記録のため、ルートレベルに `discovery` ブロックを追加:

```json
{
  "date": "2026-04-21",
  "discovery": {
    "method": "news-en",
    "description": "Perfect Daily Grind で今週のトップ記事を確認",
    "sources": ["https://perfectdailygrind.com/..."],
    "query": "arabica price april 2026",
    "freshness_hours": 14
  },
  "articles": [ ... ]
}
```

これを `record-upload.mjs` が `performance-history.json` に合流させ、後続の meta PDCA で使う。
